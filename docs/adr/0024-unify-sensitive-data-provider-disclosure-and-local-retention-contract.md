# 统一敏感数据、供应商披露与本地留存契约

Status: Accepted
Date: 2026-07-25

## 背景

原始媒体、识别分片、转写、课程上下文和模型结果都可能包含用户敏感内容，并会在
本地处理、处理缓存、运行诊断和供应商请求之间流动。仅靠日志打码或笼统的隐私
声明无法约束最小外发、路径安全、凭据处理和失败残留，也容易让操作员误解应用对
供应商留存或本地安全擦除所能作出的保证。

## 决定

统一定义机密凭据、敏感内容、受限标识元数据和可披露运行事实四类数据，并按业务
操作为 StepAudio、StepFun 和确定性 Adapter 规定最小外发集合。供应商通信强制
使用标准 HTTPS 校验，运行前、运行诊断和成功交付分别披露计划与实际外发事实。
本地文件只进入受管位置，观测使用安全字段白名单，缓存、诊断、交付和上一版按
各自明确的保留与清理边界管理。

当前数据分级、披露、路径和留存契约以
[生产就绪规格第 13 节](../production-readiness-spec.md#13-数据安全披露与留存)为准。

## 权衡

- 白名单观测会减少未知故障可直接记录的上下文，但避免正文、凭据和本地标识在
  新路径中意外泄露。
- 有效缓存默认保留到显式清理，能支持低成本复跑，却要求操作员为受管磁盘和
  备份承担持续保护责任。
- 首个生产版本不承诺应用层加密、安全擦除或供应商侧删除，缩小了实现范围，
  也要求界面和证据明确披露这些非保证事项。

## 后果

- 凭据只能在内存和供应商请求中使用；路径、文件名、运行标识、缓存标识和无关
  正文不得发送给供应商。
- Adapter、诊断、缓存维护、覆盖与回滚实现都必须遵守同一数据分类、受管路径和
  白名单披露规则。
- `cache clear` 只清理处理缓存；运行诊断、标准交付物和上一版不会被隐式删除，
  文件系统清理也不宣称达到介质级安全擦除。
