# 采用结构化运行诊断与稳定错误分类

Status: Accepted
Date: 2026-07-25

## 背景

终端文本会随详细程度和面向人的表达变化，不能可靠表示并发操作、重试、缓存、
供应商调用和发布状态。供应商异常或自由文本错误同样不适合作为自动化接口。
成功交付中的长期摘要、失败后的运行证据与进程被强制终止时的不完整事实也需要
明确区分。

## 决定

采用结构化事件日志、运行诊断清单和交付运行清单三层观测模型。正式运行通过
受约束的诊断 scope 记录带稳定事件码和严格属性 schema 的时间线，并在正常终止
时原子形成运行诊断清单。公共错误使用供应商无关的封闭注册表，稳定映射退出码、
安全消息、可重试性和操作员动作；终端只渲染这些事实，skill 调度器只消费机器
清单。

当前事件、清单、错误和耐久性契约以
[生产就绪规格第 12 节](../production-readiness-spec.md#12-运行诊断错误和终端)为准。

## 权衡

- 严格事件与错误 schema 限制了临时添加任意诊断字段的便利，但换来稳定消费、
  确定排序和默认脱敏。
- 关键边界同步和终态清单的断电安全写入增加 I/O；普通事件允许有界批量同步，
  在耐久性与运行开销之间取得平衡。
- 终端不再是权威事实来源，排查工具需要读取结构化文件，但终端格式可以独立
  演进而不破坏自动化。

## 后果

- 所有正式直播拆条运行都必须留下可关联到运行标识的诊断证据；强制终止造成的
  缺失只能标记为不完整，不能推断普通失败或成功。
- 业务模块不得直接写日志或透传供应商异常，新增稳定故障必须进入公共错误注册表
  并接受贯通验证。
- 发布提交点前无法持久化必需诊断会使运行失败；提交点后的诊断收尾故障不得撤销
  已成功发布的交付。
